# SENTINEL Standard 1.0.1

**Security Event Monitoring & Threat Detection System** — a working, single-workspace defensive security application built from SENTINEL Starter v0.1.

React + Vite + Tailwind CSS + Recharts + Lucide + React Router → FastAPI → SQLAlchemy → SQLite. Alembic manages the schema. PostgreSQL-compatible models and driver are supplied; PostgreSQL has **not** been integration-tested in this release.

Created for Pichaya Chamni (NIOR), as a portfolio project for Digital Technology for Business, Silpakorn University. Development was AI-assisted. The author should study and explain the implementation and validation honestly.

## What actually works

- Argon2id password hashing, database-backed opaque sessions, logout/revocation, absolute and idle expiration.
- HttpOnly / SameSite=Strict cookies, Secure and `__Host-` cookie naming under HTTPS configuration, trusted-origin checks and session-bound CSRF tokens.
- Admin / Analyst authorization enforced on the server. Admin can create accounts, change roles/activation, enable rules and update investigations. Analyst can read and export.
- Audit events generated by real authentication, authorization and administrative operations. No external scanner or collector is included.
- Five rule-based detections with bounded sliding windows, alert deduplication and linked evidence.
- Seven routed screens: Login, Overview, Security Events, Threat Alerts, Analytics, Reports and Settings.
- Database-driven metrics, search, severity/status filters, pagination, investigation notes and status history.
- CSV and PDF reports, including trends, risk distribution, resolution and recommendations.
- Development-only authenticated synthetic ingestion and idempotent sample-data seeding. Demo data never correlates with live data.

This is a functional educational monitoring system, **not a production SIEM, confirmed-attack classifier, or penetration-testing tool**. Do not claim enterprise readiness or independent security certification.

## Start here

See [คู่มือภาษาไทย](docs/START_HERE_TH.md) for a guided setup and five-minute demonstration.

Requirements: Python 3.12 and Node.js 22.12+ (validated with Node 24.22.1), npm and an up-to-date browser. Installing dependencies requires internet access.

From the extracted `sentinel` directory:

```bash
python -m venv .venv
# macOS / Linux:
source .venv/bin/activate
# Windows PowerShell instead:
# .venv\Scripts\Activate.ps1

pip install -r backend/requirements.txt
npm --prefix frontend ci
npm --prefix frontend run build
cd backend
# Copy .env.example to .env using your file manager, or:
cp .env.example .env
alembic upgrade head
python -m app.cli create-user --username admin --role admin
uvicorn app.main:app --host 127.0.0.1 --port 8000 --no-proxy-headers
```

Open **http://127.0.0.1:8000**. The CLI prompts for a password of 12–128 characters without echoing it. There is **no default password**, auto-login, or public registration. Keep the terminal running. Built frontend assets are served by FastAPI on the same origin, so no CORS workaround is needed.

To create an Analyst, stop the server or use another activated terminal in `backend`:

```bash
python -m app.cli create-user --username analyst --role analyst
```

Administrators can also create accounts through Settings. A local operator can reset a forgotten password with `python -m app.cli reset-password --username admin`; this revokes that account's sessions. For automated provisioning only, supply `SENTINEL_BOOTSTRAP_PASSWORD` privately in the environment and unset it immediately afterwards. Never put it in a command history, repository or screenshot.

### Enable the local demonstration

In `backend/.env`, set `DEMO_ENABLED=true` while retaining `ENVIRONMENT=development`. Restart the server. Sign in as Admin, open Settings → Generate demo events, then select **Demo dataset** in the top toolbar. Or, with the same environment:

```bash
python -m app.cli seed-demo --username admin
```

The dataset includes baseline activity and all five detection scenarios. Repeating the seed does not duplicate it. `demo/events.json` contains example ingestion payloads; `/api/demo/events` requires a valid Admin session, trusted Origin and CSRF header. It accepts only actual IP addresses in the three documentation networks. It cannot accept arbitrary external events.

### Development with hot reload

Terminal 1 in `backend`: `uvicorn app.main:app --reload --host 127.0.0.1 --port 8000 --no-proxy-headers`.

Terminal 2 in `frontend`: `npm run dev`, then open http://localhost:5173. Vite proxies `/api` to FastAPI. The default environment example trusts the exact development origins. Do not add wildcards.

### Optional Docker configuration

`docker compose up --build` builds the frontend and starts the API with a persistent SQLite volume, bound to localhost only. Create the first account using `docker compose exec sentinel python -m app.cli create-user --username admin --role admin`. Docker files are provided but were **not executed in the development environment**. No credentials are bundled. To enable demo in this local container, change the compose development setting explicitly and recreate the service.

## Upgrade from Standard 1.0

Stop the server and take a consistent database backup. Keep your existing private `.env` and database when replacing the source files. From `backend/`, run `alembic upgrade head` (do not stamp an already versioned database). Rebuild the frontend with `npm --prefix frontend ci` and `npm --prefix frontend run build` from the project root, then restart. Migration 0003 backfills the explicit rule parameters and changes AUTH-003 alert subjects/fingerprints from `tenant` to `workspace`, preserving IDs, notes, evidence and existing threshold/window/enabled settings.

Old false-positive session-probe events are retained as historical evidence; the patch prevents new ones, but does not silently delete records. They remain in historical counts until outside the selected period.

See [review fixes and limitations](docs/REVIEW_FIXES.md).

## Upgrade an existing v0.1 database

Stop writers and take a consistent SQLite backup first, including any WAL contents by using SQLite's backup API. The ZIP starter itself contained no database. If your existing database exactly matches the three-table unversioned Starter schema, point `DATABASE_URL` at the backed-up working copy and run `alembic stamp 0001` followed by `alembic upgrade head`. Never stamp a different or partially modified schema. A clean database needs only `alembic upgrade head`.

Migration 0002 retains original event/alert IDs, adds evidence/history and marks original Starter records as **demo**. It is forward-only; restore the pre-upgrade backup to roll back. A test upgrades a populated v0.1 fixture and checks record retention and referential integrity. Production migrations should run as a controlled maintenance operation, not concurrently with requests.

## Security and operating limits

- Anonymous/expired `/api/auth/me` probes return 401 without creating security events or rate buckets. Other protected-route denials remain audited.
- Session activity writes are coalesced to at most once per 30 seconds; idle expiration can be up to 30 seconds earlier than the last request would imply. Authenticated API rate counters still write and commit per request, so SQLite write contention is **not eliminated**.
- Sessions are opaque random values; only SHA-256 digests are stored for lookup. Authentication tokens never enter localStorage. CSRF state lives in memory and the session table.
- Every mutating browser request, including login, requires an explicit trusted `Origin`; authenticated mutations also require `X-CSRF-Token`.
- Login allows 8 attempts per (normalized username, trusted source IP) pair and 20 total attempts per source IP per 5-minute fixed window. Both apply whether the username exists or not. Exhausting one pair does not lock that username at a different IP. Shared NAT/proxy users can still affect one another, and rotating IPs bypasses the pair limit; see the threat model. Authenticated API calls are limited to 240/minute/user; demo writes to 60/minute/admin. Counters are atomic and DB-backed.
- No arbitrary `X-Forwarded-For` trust. The supplied runner disables proxy headers. Behind a reverse proxy, implement and test exact trusted-proxy handling or accept that all events use the proxy's address.
- Reports limit event export to 10,000 records. Detection considers at most 1,000 recent matching events per evaluation and stores at most 200 evidence links per alert.
- This release is single-workspace: Analysts can see all workspace security records. It is not tenant-isolated.
- Database administrators can alter logs. There is no tamper-proof log archive, MFA, external ingestion agent, notification service, or automated containment.
- Working hours are a configured rule, not learned behavior. Alerts are indicators, not proof of compromise.
- Session cleanup: `python -m app.cli cleanup`. Define retention and backups before long-term use; this release does not delete security history automatically.

For a future HTTPS deployment set `ENVIRONMENT=production`, `COOKIE_SECURE=true`, `DEMO_ENABLED=false`, exact HTTPS `TRUSTED_ORIGINS` and explicit `ALLOWED_HOSTS`. Add TLS, protected database/backups, operations monitoring and a security review. The application refuses unsafe production combinations. No public deployment was performed; the available site host does not directly run this requested Python stack.
